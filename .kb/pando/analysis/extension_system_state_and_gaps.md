# Extension system — state, open-source independence, and everything still unimplemented

Written 2026-08-26, after P6 closed. Two questions this document answers:

1. **Does the open-source build depend on the private `alchemai-agent` repository?**
   Verified answer: **no**, and the enterprise code is optional by construction. Method and
   results in §3.
2. **What is left?** §4, ranked in §5.

Companion documents: the design analysis is
[[pando/analysis/extension_system_enterprise_analysis]]; each phase has its own change record
([[pando/changes/extension-system-p0-foundations]] … [[pando/changes/extension-system-p6-licensing-hardening]]).

### 1.1 Capability interfaces that exist

`pkg/extension` is still **stdlib-only** (verified: `go list -deps ./pkg/extension` returns nothing
outside the standard library and the package itself — notably no cobra, because `CommandProvider`
declares commands as data and `internal/extensions/commands.go` builds the cobra tree from that).

Lifecycle: `Extension`, `Provisioner`, `Validator`, `CleanerUpper`, `Lifecycle`, `ConfigView`.
Capabilities: `ToolProvider`, `Tool`, `ToolMiddleware`, `ToolFilter`, `ToolInterceptor`,
`CommandProvider`, `SlashCommandProvider`, `HTTPEndpointProvider`, `HTTPMiddlewareProvider`,
`EventSubscriber`, `FrontendProvider`, `FrontendOverlay`, `FrontendReplacer`, `MemorySink`,
`MemorySyncReporter`, `RemembranceSearcher`, `RemembranceSearchWrapper`, `LicenseProvider`.

Adding a capability is non-breaking by construction (type assertion), which is why the two missing
ones in §4.1 are a scheduling question and not a design debt.

## 2. The dependency direction, stated once

```
alchemai-agent (private)  ──requires──▶  pando (public)
pando (public)            ──requires──▶  nothing private

xpando build  ──generates──▶  a third, throwaway main module
                              that requires BOTH and blank-imports the enterprise packages
```

The public repository contains **no** import of the private module, no `require` on it, and no
build-tagged file that would introduce one. The enterprise packages register themselves through
`init() { extension.Register(...) }`; the only thing that pulls them into a binary is the generated
`main.go` that `xpando` writes outside both repositories:

```go
// Code generated by xpando. DO NOT EDIT.
package main

import (
	pandocmd "github.com/digiogithub/pando/cmd"

	_ "github.com/digiogithub/alchemai-agent/memorysync"
	_ "github.com/digiogithub/alchemai-agent/license"
)

func main() { pandocmd.Main() }
```

This is the xcaddy model, and it is what makes the enterprise code **optional**: the standard build
is not "the enterprise build with features switched off", it is a binary in which that code was
never linked. `extension.Register` is never called for it, so it cannot appear in
`pando extensions list`, cannot be enabled by configuration, and cannot be reached by an operator
who edits `.pando.toml`.

The `enterprise` build tag is deliberately **inert in the public repository** — there are zero
`//go:build enterprise` files in it. The tag survives only to stamp `version.Variant` and to keep the
CI matrix honest about tag-guarded code; it is not the composition mechanism, and expecting it to be
one is the misreading this section exists to prevent.

## 3. Open-source independence — verification

### 3.1 What the isolation rests on

Four structural rules, all currently holding:

1. **No `require` on the private module in `go.mod`.** A single `require` would break `go mod
   download` for every OSS user, with or without a build tag, because module resolution happens
   before tag evaluation.
2. **No blank-import file in the public repository, tagged or not.** This was the first thing
   learned in P0: a `//go:build enterprise` file blank-importing the private module still forces a
   `require`, and still breaks `go mod tidy` for OSS users. The composition file therefore lives in
   a generated module, not in the repository.
3. **Registration is `init()`-driven, not configuration-driven.** Nothing in core names an
   enterprise extension. The manager iterates whatever registered itself.
4. **The gate degrades to "ungated", not to "broken".** With no `LicenseProvider` linked in, the
   manager gates nothing and logs that once (P6). An OSS build never reports an extension as
   `unlicensed`, and `pando extensions list --json` emits no `license` object at all.

### 3.2 Checks performed 2026-08-26

| Check | Command | Result |
|---|---|---|
| No private module in `go.mod` / `go.sum` | `grep -rn alchemai go.mod go.sum` | no match |
| No Go source references it | `grep -rn alchemai --include=*.go .` | only comments in `pkg/extension/doc.go` and `cmd/xpando/main.go` usage examples |
| No tag-guarded enterprise file | `grep -rn "go:build enterprise" --include=*.go .` | no match |
| Not in the build graph, any tag set | `go list -deps ./...`, `-tags enterprise`, `-tags "enterprise enterprise_ui"`, each piped to `grep -i alchemai` | empty in all three |
| Not in the module graph | `go list -m all \| grep digiogithub` | only `github.com/digiogithub/pando` |
| Compiles under every tag set | `go build ./...`, `-tags enterprise`, `-tags enterprise_ui` | all clean |
| **A real OSS clone, offline, with no private credentials** | tracked files only (`git ls-files`) copied to a scratch tree, then `env -u GOPRIVATE GOPROXY=off go mod tidy` and `go build ./...` | `tidy` succeeds, **`go.mod` byte-identical afterwards**, build succeeds |

The last row is the decisive one. `GOPROXY=off` means any attempt to resolve a module not already in
the local cache fails hard, and the private module is not in that cache path for an OSS user;
`-u GOPRIVATE` removes the credential configuration entirely; copying only `git ls-files` output
reproduces exactly what a `git clone` yields. `go mod tidy` leaving `go.mod` unchanged proves no
package in the tree — under any tag — imports anything the manifest does not already declare.

### 3.3 What would break it, i.e. what to watch in review

- Any `require github.com/digiogithub/alchemai-agent/...` reaching `go.mod`, however it got there
  (an editor's auto-import, a `go get` run in the wrong directory, a `replace` left behind after
  local testing).
- A `//go:build enterprise` file in the public repository that imports the private module. Tags do
  not defer module resolution.
- Moving `xpando`'s generated `main.go` into `cmd/` "for convenience".
- A test fixture in core that imports an enterprise package to exercise a capability. Use the
  in-repo fakes in `internal/extensions/*_test.go` instead; that is what they are for.

A cheap regression guard would be a CI step running the §3.2 offline check on every PR. It does not
exist yet — `build-matrix.yml` builds both tag sets, which catches (3) but not (1).

## 4. Not implemented

### 4.1 `ControlPlaneClient` and the two core interfaces it needs

The only item the design analysis itself still lists as open (§8.6-Q5). Multi-tenancy is out of
scope for Pando: one instance, one internal user, tenancy handled by a remote control plane above
it. That decision created the contract question — how the remote layer injects identity, license and
configuration into an instance, and how it reads instance state back — and nothing has been built.

Two interfaces from the §6.3 sketch were never implemented, and both are the core-side surface this
work needs:

- **`HTTPAuthProvider`.** P2 shipped `HTTPMiddlewareProvider` instead, which runs *inside* core's
  CORS, basic-auth and token checks. It can add to authentication; it cannot replace it. Validating
  a token minted by the control plane, or WebUI SSO, needs an extension that runs *as* the
  authenticator.
- **`ConfigProvider`** (`LoadConfig() (map[string]any, error)`). An instance whose configuration is
  pushed from a control plane needs a config source that is not a file on disk.

Treat these as part of the control-plane work rather than as separate backlog items; designing them
without knowing the control-plane contract would be designing twice.

### 4.2 `alchemai-agent/memorysync` has no tests at all

Seven source files, zero test files:

| File | What is untested |
|---|---|
| `redact.go` | which fields are stripped before an event leaves the machine |
| `merge.go` | dedup and merged local/remote reads |
| `queue.go` | batching, retry, backoff |
| `spool.go` | on-disk spill and recovery |
| `transport.go` | `statusError`'s permanent/retryable split, the 512-byte detail cap, `toPayload` field mapping |
| `config.go`, `extension.go` | option validation, dry-run, lifecycle |

This is the largest real gap in the whole system and the only one whose failure mode is *customer
data*, not a missing feature. `redact.go` decides what crosses the network and no automated check
exercises it. `transport.go` was written last (2026-08-25) and has never run against anything.

Priority cases, roughly in order: redaction of every field in `MemoryEvent`; `toPayload` mapping
(the file's own comment argues a core rename must be a compile error here — a test would make it a
test failure too); 4xx-vs-429-vs-5xx classification; spool round-trip; dedup on replay.

By contrast `license/` has 7 tests covering the valid, unentitled, untrusted-key, missing-file,
no-keys-in-build, unprovisioned and env-override paths.

### 4.3 No signing key exists, and no release path passes one

`license/keys.go` still holds the placeholders: `linkedKeyID = ""`, `linkedKeyB64 = ""`,
`bakedKeys = map[string]string{}`. No key pair has been generated or stored, and no release rule
passes the `-ldflags` line that `mklicense keygen` prints.

Consequence: an enterprise binary built today contains no trusted keys, so `trustedKeys()` returns
`this build contains no trusted license keys` and **every** enterprise module is refused. That is the
correct failure — it is loud, and it names the cause — but it means the licensing chain has never
been exercised end to end with a key that outlives a test run. What is missing is operational, not
code: generate the first key pair, store the private half where the release pipeline can read it and
nowhere else, and add the `-ldflags` to the enterprise build rule.

### 4.4 No nightly compat job in the private repository

§8.6-Q1 required it in as many words: the private repo must run a compat job against core `main`
nightly, or the enterprise build rots silently. `alchemai-agent` has no `.github/` directory at all.

`compat/` exists and is exactly the right probe — it asserts at compile time that the enterprise
types still satisfy every core interface, `extension.LicenseProvider` included — but nothing runs it
on a schedule. Today a breaking change to `pkg/extension` is discovered whenever somebody next
builds an enterprise binary by hand.

### 4.5 Frontend capabilities never exercised in a browser

From the P4 record: `FrontendOverlay` and `FrontendReplacer` are unit-tested only, and no browser has
actually imported a panel through the `window.__PANDO_UI__` contract. Separately, the alternative
enterprise `dist` that §8.6-Q2 describes does not exist — that is product work, not roadmap work, but
it means `FrontendReplacer` has no real consumer yet.

### 4.6 Smaller items

- No WebUI surface for licence state. `pando extensions list` and `GET /api/v1/extensions/license`
  cover reporting. Deliberate: unlike the memory sink, nothing leaves the machine here, so the
  permanent-visibility rule that governs corporate memory does not apply.
- No CI guard for §3.2 (see §3.3).
- The `✅ DONE` markers missing from P1-P4 in the design analysis (§1).

## 5. Suggested order

1. **`memorysync` tests** (§4.2). Highest risk, entirely independent of every other item, and the
   only one where being wrong means customer data went somewhere it should not have.
2. **Nightly compat job** (§4.4). An afternoon; it is what stops the other work from decaying while
   attention is elsewhere.
3. **First signing key and the release `-ldflags`** (§4.3). Blocks shipping anything enterprise.
4. **Control-plane contract** (§4.1), with `HTTPAuthProvider` and `ConfigProvider` designed as part
   of it.
5. Frontend exercise in a browser (§4.5), when there is an enterprise `dist` to point it at.
6. Documentation markers and the CI isolation guard (§4.6).

## 6. Commands, for re-running §3

```bash
# In the core checkout.
grep -rn alchemai go.mod go.sum                       # expect: nothing
grep -rn alchemai --include=*.go .                    # expect: comments only
grep -rn "go:build enterprise" --include=*.go .       # expect: nothing
go list -deps ./... | grep -i alchemai                # expect: nothing
go list -tags "enterprise enterprise_ui" -deps ./... | grep -i alchemai
go list -m all | grep digiogithub                     # expect: only pando itself

# The clone-and-build-offline check.
S=$(mktemp -d)
git ls-files -z | tar --null -T - -cf - . | tar xf - -C "$S"
cd "$S"
env -u GOPRIVATE GOPROXY=off go mod tidy && git diff --no-index go.mod "$OLDPWD/go.mod"
env -u GOPRIVATE GOPROXY=off go build ./...
```
