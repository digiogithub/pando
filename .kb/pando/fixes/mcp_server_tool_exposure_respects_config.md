# Fix: MCP server mode now mirrors user config for tool exposure

**Date:** 2026-07-24
**File:** `cmd/mcp_server.go`

## Problem

`pando mcp-server` exposed tool groups the user had disabled. Root cause was
`enableMCPServerFeatures()`, which ran before `app.New` and force-set global
config flags regardless of the user's configuration:

- `cfg.Mesnada.Enabled = true` (mesnada / subagent tools always exposed)
- `cfg.Remembrances.Enabled = true` (KB + code tools always exposed)
- `cfg.Remembrances.MemoryEnabled = true` (remember/recall/forget always exposed)
- `cfg.InternalTools.FetchEnabled = true`
- `cfg.InternalTools.BrowserEnabled = true` (10 browser tools always exposed)
- auto-enabled google/brave/perplexity/exa search whenever an API key was
  present, even if the user had set the corresponding `*Enabled = false`

Viper code defaults (no `.pando.toml`) have mesnada/remembrances/memory/browser
= false, so the forcing overrode both explicit user disable and the safe
default. API-key gating (`Enabled && key != ""`) already existed in
`buildMCPServerTools`, but the `Enabled` flag itself was being forced on.

## Change

Rewrote `enableMCPServerFeatures()` to derive nothing by force. It now only
turns on the subsystem a dedicated, opt-in `[MCPServer]` feature proxies:

- `MCPServer.GatewayExpose.Enabled` -> `MCPGateway.Enabled`
- `MCPServer.SelfImprovement.Enabled` -> `Evaluator.Enabled`

Everything else mirrors the user's global config:

- Mesnada/subagent tools: gated by `appSvc.MesnadaOrchestrator != nil`, which
  `app.New` builds only when `cfg.Mesnada.Enabled`.
- Remembrances (KB + code + events): gated by `appSvc.Remembrances != nil`,
  built only when `cfg.Remembrances.Enabled`.
- Memory tools: gated by `cfg.Remembrances.MemoryEnabled`.
- Fetch/browser: gated by `InternalTools.FetchEnabled` / `BrowserEnabled`.
- Search engines: gated by `*Enabled && apiKey != ""` (unchanged).

No changes needed in `buildMCPServerTools` — its existing per-group gates now
see the real config instead of forced values.

## Design decision

Chosen approach: mcp-server = mirror of global config (over dedicated per-group
`[MCPServer]` toggles). Simple and predictable. Trade-off: a user with no
`.pando.toml` gets only cache + fetch + context7 (viper defaults); a config
generated by `pando init` enables the full set, so out-of-box via init is
unchanged. Users wanting a specific set enable it in their global config.

## Tool registration note

In `pando mcp-server`, `buildMCPServerTools()` (passed as `PandoTools`) is the
single source of exposure. The mesnada `Server.registerTools()` takes the native
`validPandoTools()` branch and returns early, so the server's own
`buildRemembrancesLLMTools(s.remembrances)` set is NOT additionally exposed in
this mode.
