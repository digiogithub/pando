# Feature: incremental per-message session indexing (#6) (2026-09-11)

Implements roadmap item #6 of [[pando/plans/sqlite_contention_fix_roadmap.md]], ranked #6 in [[pando/analysis/session_index_locked_residual_risk.md]] section 5. Builds directly on the design sketch at the end of [[pando/fixes/session_indexer_debounce_retryable_busy.md]] and on step 1's IMMEDIATE-tx/pragma/`idx_events_session` work in [[pando/fixes/sqlite_immediate_tx_conn_pragmas_session_index.md]].

## Problem recap

`internal/app/remembrances_indexer.go` used to rebuild the **whole** session transcript on every qualifying event, re-embed **all** chunks (`EmbedDocuments`), and call `EventStore.ReplaceSessionEvents` (replace-all). For a 1,420-chunk session that is O(n) embedding + an O(n) write transaction holding the SQLite write lock (head-of-line blocking of the prompt path) and ~12 MB of JSON over IPC per run on secondaries, forwarded via the writecoordinator to the primary's `RemembrancesWriteDispatcher`.

## Design decisions

- **Chunk layout**: one message = one plan entry. Its text is chunked with the existing `embeddings.ChunkText`/`DefaultChunkSize`/`DefaultChunkOverlap` logic only if it exceeds the chunk size (same as before, just scoped to one message instead of the whole transcript). Each row's metadata carries `session_id`, `message_id`, `content_hash`, `chunk_index`, `chunk_count`, plus the existing `title`/`source`/`message_count`/`updated_at`/`user_id` fields (duplicated onto every row, matching the pre-existing convention rather than introducing a separate session-only row type).
- **Staleness marker**: a content hash (`sha256` hex, `contentHashHex` in `internal/app/session_index_incremental.go`), not `updated_at`. The hash source is the message's rendered role+parts text (`extractMessageSearchParts`), **excluding** the session title. A message is skipped entirely (no embed, no write) when its stored `content_hash` still matches.
- **Header row for session-level data**: a synthetic `message_id = "__session_header__"` (`sessionHeaderMessageID`) row carries `"Session title: <title>"`, hashed on the title text alone. This keeps the session searchable by title even when no individual message restates it, and — because its hash excludes everything but the title — a **title-only change re-embeds just this one row**, not the whole session. Confirmed by `TestIndexSessionConversation_HeaderRowUpdatedOnTitleChange` (embedder called exactly once after a title change, and no message's own marker hash moves).
- **Short-message handling**: rather than skipping trivially short messages (risking lost recall for meaningful short replies like "yes"/"ok"), every per-message chunk is uniformly prefixed with `"Session: <title>\n"` before the `"ROLE:\n"` line (`messageIndexContent`). This gives short/ambiguous messages disambiguating context for both semantic and FTS search without special-casing length. Trade-off: since the *hash* excludes the title (previous bullet), a message's *indexed text* can show a stale title until that message's own content next changes — judged acceptable since the header row always has the current title, and per-message title staleness is cosmetic context, not the primary search key.
- **Lazy migration, no backfill script**: `EventStore.SessionHasLegacyRows(ctx, sessionID, subject)` does a cheap read (`subject = ? AND json_extract(metadata,'$.session_id') = ? AND json_extract(metadata,'$.message_id') IS NULL LIMIT 1`, narrowed by `idx_events_session` before the `IS NULL` filter). If true, `indexSessionConversation` does one delete-only `ReplaceSessionEvents(ctx, sessionID, subject, nil, nil, nil)` call (no embedding) to clear every row for that session, then continues into the incremental path with an empty marker set — so every message in that session is treated as new exactly once, on its first post-upgrade run. Legacy and per-message rows for the same session never coexist.
- **Version-skew fallback**: see IPC section below.
- **Retry-on-busy and scheduler**: unchanged, reused as-is. `replaceSessionEventsWithRetry` (name kept for compatibility with existing tests, despite now wrapping message-level writes too — it was already generic, taking any `func() error`) wraps every `ReplaceMessageEvents`/`DeleteMessageEvents`/`ReplaceSessionEvents` call. `sessionIndexScheduler` (debounce/min-interval/dirty-trailing-run) is untouched.

## Result-shape change for consumers

Audited every reader of session events (`subject = 'session'`): `internal/llm/tools/remembrances_events.go` (`search_events`/`save_event` tools), `internal/llm/tools/remembrances_hybrid.go` (`hybrid_search_remembrances`), `internal/rag/hybrid.go` (`RemembrancesService.HybridSearch`), `internal/rag/enricher.go` (context-enrichment `searchEvents`), `internal/llm/prompt/capabilities.go` / `internal/llm/tooldiscovery/policy.go` (tool-name lists only). None of them assume `chunk_index`/`chunk_count` are contiguous over a whole transcript, and none dedup by session in a way per-message rows would break — every one already just iterates `SearchResult{Event, Score, Rank}` and prints `Event.Content`/`Event.Metadata`. **No code changes were needed in any of these files.**

**Visible behavior change**: a search hit's `content` is now typically one message's text (or one chunk of an oversized message) instead of an arbitrary window that could previously span multiple messages of the old flattened transcript. This is a quality improvement for "jump to this message" style consumption, at the cost of losing the old cross-message windowing for very short exchanges — mitigated by the title-prefix decision above. `hybrid_search_remembrances`/`search_events` results also now include a `"__session_header__"` synthetic entry when a title-only match ranks highly; this is intentional (titles are otherwise unsearchable) and distinguishable via `metadata.message_id == "__session_header__"`.

## IPC protocol addition + version-skew handling

Two new proxied write methods, `"ReplaceMessageEvents"` and `"DeleteMessageEvents"`, added to the existing `db.write` / `RemembrancesWriteDispatcher` switch — same envelope (`WriteRequest{Meta, Method, Params}`) and same code path (`DBProxy.WriteWithRetry` → `proxyVoidWrite` → `db.write` JSON-RPC → `dispatchWrite`'s default case → `RemembrancesWriteDispatcher.DispatchRemembrancesWrite`) as every other remembrances write.

**Version skew**: during a rolling upgrade, a secondary running this code can talk to an older primary binary whose `RemembrancesWriteDispatcher` switch predates these two methods. That primary's default case returns `fmt.Errorf("rag dispatcher: unsupported remembrances write method %q", method)`, which crosses the IPC boundary as plain text (the JSON-RPC layer flattens it to a message-only `rpcError`) and is re-wrapped as `"ipc: RPC error -32000: ...: unsupported remembrances write method ..."` on the secondary. `dbproxy.mapToWriteError` now recognizes that text (and `dispatchWrite`'s own `"unknown write method"` text, for completeness) as `ErrCodeMethodNotFound` (not retryable), and `dbproxy.IsMethodNotSupportedError` recognizes the resulting `*WriteError`. `App.indexSessionConversation` checks this on the **first** `ReplaceMessageEvents`/`DeleteMessageEvents` failure in a run and, if it matches, abandons the incremental path for that run and calls `indexSessionConversationFullRebuild` — the exact pre-#6 whole-transcript rebuild — instead, so the session's index is never left straddling both row layouts. Once every instance in a deployment is upgraded, this path is never reached again.

**Known test gap**: the version-skew *detection and mapping* (`mapToWriteError`/`IsMethodNotSupportedError`) is unit-tested directly, and the dispatcher's exact error text is pinned by a round-trip test in `internal/rag/proxy`. The *end-to-end* switch inside `indexSessionConversation` (catching `IsMethodNotSupportedError` and actually calling `indexSessionConversationFullRebuild`) is implemented per the design above but is **not** exercised by an automated test that drives it through a real two-process primary/secondary IPC round trip — `dbproxy.DBProxy.client` is a concrete `*ipc.Client` with no seam for a fake, and building a genuine multi-process harness was judged out of scope for this change. Risk: low (the branch is a simple two-line `if dbproxy.IsMethodNotSupportedError(err) { return ...FullRebuild(...) }`, and its two inputs — the error classification and the fallback function itself — are each independently tested), but it is the one code path in this feature without a direct test.
