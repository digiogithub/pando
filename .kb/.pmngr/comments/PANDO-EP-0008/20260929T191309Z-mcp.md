Closed 2026-09-29. Outcome: only PANDO-US-0036 was implemented (cache-stable, query-aware memory injection; see `.kb/pando/changes/cache_stable_memory_injection.md`). The rest was cancelled by the maintainer after the pros/cons review (`.kb/pando/analysis/grok-build-memory-pros-cons.md`):

- **US-0037 (user scope, storage outside repo, tombstones) — rejected.** No per-user memory store: memory hidden in the user profile is hard to find and back up and dies with the machine. Personal memory, when needed, lives in a personal repository; a primary Pando there launches Pando instances in other repositories as subagents to reach each project's own memory, so all memory stays in versioned repos. jj history makes a tombstone ledger unnecessary.
- **US-0034 (automatic capture) — rejected.** An extra LLM call per turn/session brings no clear advantage: Pando already persists sessions and events and makes them searchable, so prior context is recoverable without automatic `remember`. The dead `MemoryAutoCapture` setting was removed in US-0036.
- **US-0035 (Dream consolidation) — rejected.** The KB is versioned and human-edited; LLM rewrites would churn history, conflict with humans and risk losing detail. Versioned history, KB front matter and wiki links are enough.
- **US-0033, US-0038, US-0039 — cancelled** as they only served the rejected features (reference, rollout/UX for capture, synthesis).

The epic's original "no code changes" constraint was lifted by the maintainer for US-0036.
